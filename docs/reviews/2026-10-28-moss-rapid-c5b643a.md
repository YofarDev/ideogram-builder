## R1 — [P2] A capabilities refresh can permanently remove queued Rapid jobs

Location: `src/queue.js:67–73`, called at dispatch on line 118;
`src/settings-moss.js` clears capabilities before awaiting the refresh.

`checkSnapshot()` treats null capabilities as the original three presets.
`snapshotGuard()` then removes an invalid job from the queue immediately.
During a same-backend, same-endpoint refresh, null means the request is still
pending (or failed), not that the server withdrew Rapid. If the running job
finishes during that interval, a previously accepted Rapid job disappears,
with only a temporary toast, even if the refresh subsequently advertises it.

The reproduction accepts a 1024² Rapid snapshot, sets capabilities to null on
that same Modal endpoint, and rejects the unchanged snapshot. The new queue
test already exercises the permanent removal but interprets unknown metadata
as an authoritative withdrawal.

Keep queued jobs while availability is unknown: wait for refresh, retain the
last known endpoint-specific capabilities for accepted jobs, or show a blocked
state. Do not permanently remove them merely because a metadata request is in
flight. Test an actual deferred refresh resolving to the same Rapid support.

## R2 — [P2] MOSS collection jobs can silently use the Ideogram preset

Location: `src/queue.js:52–56`.

The model override only switches to `state.moss.preset` when the original
preset is absent from `MOSS_PRESET_IDS`. `Quality` and `Turbo` are valid names
in both models. With the editor on Ideogram/Quality and the saved MOSS choice
on Rapid, generating a MOSS collection item submits **Quality**, not Rapid.
The availability pre-check validates the MOSS Rapid selection, so it does not
catch this mismatch.

The reproduction runs `enqueueImportJson('{}', {model:'moss'})` through the
real queue with those states and captures `snapshot.preset === 'Quality'`.
This can turn an intended four-step request into a 50-step request.

Resolve the preset from the effective model, rather than testing whether a
name happens to exist in both model namespaces. Add both Quality and Turbo
collision cases to the collection queue tests.

## R3 — [P2] The OCR aggregation rewards missing required text

Location: `runpod/moss_benchmark.py:623–626`.

The entire OCR transcript is compared separately with every expected string,
then the minimum CER is used. For expected `['HELLO', 'WORLD']`, the actual
review-sheet code scores a correct transcript `HELLO WORLD` as **1.200**, but
an incomplete transcript `HELLO` as **0.000**. Additional required text is
penalized as insertions, while omitted labels can be ignored completely.

This makes the score unsuitable for the proposed one-percentage-point text
quality gate. Compare a consistently ordered complete reference transcript
with the complete OCR transcript, or match annotated regions and aggregate
edit counts/reference lengths while charging missing regions as deletions.
Test correct multiple labels, omissions, extra text and digit substitutions.

## R4 — [P2] Switch and steady-state timings are still combined

Location: `runpod/moss_benchmark.py:485–489`; switch flag at lines 382–383.

`switched` is recorded but omitted from `cohort()`. `summarize()` therefore
combines it with steady-state observations and reports no separate switch
latency distribution. Two otherwise identical complete records—steady 1,000 ms
and switched 9,000 ms—produce one row with a 5,000 ms median.

Also, `last_executed_config` tracks measured jobs only. A warmup can already
switch to and initialize the new preset, after which its measured job is still
flagged as a switch. That flag does not reliably identify actual switching cost.

Track configuration changes across every executed job, including warmups, and
report switch/steady observations separately. Use the same distinction in the
regression guard. Test a switch with a preceding warmup and one without it.

## R5 — [P2] Worker identity does not change when the benchmark restarts ComfyUI

Location: `runpod/handler.py:103–110`; lifecycle in
`runpod/moss_benchmark_worker.py:36–50`.

The UUID is created when the parent handler module imports, not when a ComfyUI
server starts. `BenchmarkWorkers` stops/restarts the child for profile changes
but retains that module and parent process. The newly counterbalanced job
ordering revisits profiles, so different physical server lifetimes can share
one identity and be merged into a worker cohort.

Running the real benchmark manager with baseline → Rapid → baseline produces
three lifecycle startups but the same handler worker ID for all three.

Create the identity at actual worker/server startup, pass it to the parent
handler and child diagnostics, and keep it stable only for that lifecycle.
Refresh the relevant warmup bookkeeping when a server is replaced. Test a
profile round trip, not just repeated calls within a single imported module.

## R6 — [P2] Capabilities no longer honor a narrower validated area limit

Location: `runpod/moss_config.py:544–545`; request check at lines 512–514.

`max_area_mp` now comes only from the technical preset/profile limit, while
requests still enforce `validated_presets[preset]`. If validation covers a
smaller area, the GUI advertises a size the handler rejects. For example,
setting the supported validation map entry `Fast: 0.5` advertises no limit,
while a 1024² request is rejected as above 0.5 MP.

This does not change the proposed Rapid 1 MP preview where both limits agree,
but it regresses the independent validation-limit contract used for promotion.
For validated entries, advertise the minimum applicable technical and
validated limits. For experimental entries, advertise the technical limit.
Test differing limits rather than only equal Rapid limits.
